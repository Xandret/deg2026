# 01. Парсер сырого дампа блокчейна (`deg.sources`, `deg.parse_blocks`, `deg.build_db`, `deg.validate_slotin`)

## Зачем свой парсер
По решению №6 (docs/decisions.md) все данные курсовой получаем сами из сырых блоков, а опубликованные
таблицы С. Слотина используем только как эталон для сверки.

## Откуда берутся блоки
Единственный полный дамп — **day3** (20.09 18:08–21:51 МСК, все 7 цепочек). `deg.sources.plan()`
собирает непрерывное покрытие:

| Цепочка | Блоки | Откуда |
|---|---|---|
| shard-0 | 1–27500 | `edg_day3_safe.tar` (tar обрезан в конце, но эти члены целые) |
| shard-0 | 27501–32630 | распакованный каталог |
| shard-1…6 | 1–≈32629 | распакованные каталоги |

Проверено: разрывов нет ни в одной цепочке. Файлы `*.history-*` (старые версии хвостовых чанков)
пропускаются. Tar не сжат → данные члена читаются по смещению `offset_data`, без распаковки на диск.

**Полнота day3 (проверено полным прогоном 24.09):** в дампе есть `finishVoting`, `decryption`,
`commissionDecryption` и `results` по **всем 5 103 контрактам** — расшифровка прошла до 21:51 20.09.
Публичный `edg2026.tar` для итогов не нужен; он остаётся только как независимая копия для сверки хешей.

## Устройство блока (Waves Enterprise)
```
блок: height, timestamp (мс UTC), generator, signature, reference, transactions[]
  транзакция type=105  — «результат исполнения контракта», подписана нодой; timestamp = outer_ts
    tx: type=103 — создание контракта (одно голосование = один контракт)
        type=104 — вызов контракта; timestamp = tx_ts; contractId
      params[]: operation = …
    results[]: что контракт записал в состояние (VOTE_…, BLINDSIG_…, RESULTS …)
  type=1/101/110 — служебные (генезис-блок: выдача ролей и т.п.)
```

### Операции контракта
| operation | Смысл | Ключевые параметры | Таблица |
|---|---|---|---|
| (type 103) | создание голосования | pollId, commissionId, bulletinHash, dimension, blindSigType | `contracts` |
| addMainKey | публикация ключей шифрования | mainKey, commissionKey, dkgKey | `contract_events` |
| startVoting | старт | dateStart | `contract_events` |
| addVotersList | начальный список избирателей УИК | userIdHashes[], primaryUikRegionCode, primaryUikNumber, votersCount | `list_events` + `list_hashes` |
| blindSigIssue | **выдача бюллетеня** | data=[{userId, maskedSig}], регион, УИК | `ballots` |
| vote | **приём голоса** | vote (шифротекст ≈5 КБ), blindSig; УИК нет — это и есть тайна голосования | `votes` |
| removeFromVotersList | исключение из списка (голосовал на участке, досрочно, умер) | userIdHashes[], регион, УИК | `list_events` + `list_hashes` |
| decryption, commissionDecryption | расшифровка итогов | — | `contract_events` |
| results | итог | RESULTS = [[голоса по позициям]] | `contract_events` (payload целиком) |

Регион — код субъекта в `primaryUikRegionCode` (22 — Алтайский край, 31 — Белгородская, 66 — Свердловская,
**90 — Пермский край** (не 59!), 93 — Крым). Справочник регион/выборы/кандидаты в цепочке отсутствует —
в контракте только `bulletinHash`; названия берём из API портала stat.vybory.gov.ru (отдельный модуль).

### Три отметки времени
- `tx_ts` — внутренняя транзакция (сервис ДЭГ сформировал вызов). **Основное время** (так же у Слотина).
- `outer_ts` — нода исполнила контракт: в среднем на ~13 с позже `tx_ts`.
- `block_ts` — начало формирования блока: на ~2 с раньше `outer_ts`.
В `build_db` время переводится в «наивное» МСК: `ts_msk` (мс) и `ts_msk_s` (секунды).

## Наблюдения о приватности (важно для текста и сайта)
- `user_id` в `blindSigIssue` **одинаков для одного человека во всех его контрактах** (в пробной выборке
  163 618 бюллетеней → 132 539 разных `user_id`). Это позволяет считать людей, а не бюллетени.
- Хеши в списках (`userIdHashes`) тоже сквозные между контрактами, но **не совпадают** с `user_id`
  бюллетеня (проверено: 0 совпадений из 660) — связать «кто из списка получил бюллетень» нельзя. Так задумано.
- Голос (`vote`) не содержит ни УИК, ни `user_id`.
- `list_hashes` и `user_id` — псевдонимные идентификаторы. Используем только в агрегатах, наружу
  (сайт, репозиторий, текст) не публикуем никогда.

## Параллельная обработка
- Один чанк = одна задача процесса (`multiprocessing`, режим `spawn` — единственный в Windows).
- Результат чанка — parquet-файлы по таблицам, запись через временный файл + `os.replace` (атомарно).
- Маркер `_done/<чанк>.json` → повторный запуск пропускает готовое (можно прерывать Ctrl+C).
- Крупные чанки идут первыми — меньше простоя в конце.
- Ошибка одного чанка не роняет прогон: попадает в `_summary.json`, код возврата 1.

## Сверка со Слотиным (`validate_slotin`) — результат полного прогона 24.09.2026
Мультимножества событий сравниваются счётчиками по ключу (учитывает дубликаты), по частям по
`hash(contract_id)` — чтобы влезть в память слабой машины.

| Проверка | Наши | Слотин | Только у нас | Только у Слотина |
|---|---|---|---|---|
| A. Бюллетени (всего) | 12 202 035 | 12 202 035 | — | — |
| A. Голоса (всего) | 12 088 374 | 12 088 374 | — | — |
| A. Начальные списки (Σ) | 13 542 183 | 13 542 183 | — | — |
| A. Исключения из списков (Σ) | 122 442 | 122 442 | — | — |
| A. Контракты | 5 103 | 5 103 | — | — |
| B. Бюллетени (контракт, УИК, секунда) | 12 202 035 | 12 202 035 | 0 | 0 |
| C. Голоса (контракт, секунда) | 12 088 374 | 12 088 374 | 0 | 0 |
| D. События списков (контракт, УИК, секунда, число, тип) | 257 733 | 257 733 | 0 | 0 |
| E. Итоги (RESULTS по контракту) | 5 103 | 5 103 | равны все 5 103 | |
| F. Покрытие контрактов | — | — | 0 | 0 |

**Вывод:** независимый парсер воспроизводит опубликованные таблицы полностью, без единого
расхождения. Для текста: «данные получены автором независимо из сырого дампа блокчейна; сверка с
открытым набором С. Слотина (github.com/sslotin/elections) показала полное совпадение по всем 24,5 млн
событий и итогам всех 5 103 голосований». Отчёт: `data/derived/validation_slotin.json`.

Первый полный прогон выполнен в Linux-VM (2 ядра, лимит ~95 с на команду): парсинг ≈ 25 минут
чистого времени частями по 70–160 с (флаг `--time-budget`), сборка базы и сверка — по таблицам
(`build_db --only`, `validate_slotin --checks --partitions 8`).

## Порядок запуска (Windows)
```
setup.cmd
run.cmd parse_blocks --workers 12      (≈2 800 чанков, 44 ГБ gzip)
run.cmd build_db
run.cmd validate_slotin
```
